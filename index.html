Welcome & Goals

0:00 - 0:10

Welcome to the Brown University Health Automation & Governance Hands-On Lab. In the next two hours, you will replace a hand-coded Epic Clarity import with a parameterized, observable, governed pipeline - and watch it handle unexpected input along the way.

What we will build

  1. Configuration-driven imports - one procedure, any Clarity table
  2. Resilient vendor ingestion - validation, quarantine, schema drift detection
  3. Centralized logging - structured events, operational dashboards
  4. Governance & masking - reusable policies that mask data by role
  5. AI capstone (optional) - automated annotation of clinical notes and imaging metadata

What this is NOT

This is not a feature tour. Every exercise connects to the same pipeline. The goal is one working workflow, not seven disconnected demos.

Prerequisites

  1. Get a Snowflake trial (if you do not already have an account): signup.snowflake.com - choose Enterprise edition, any cloud/region
  2. Log in to your Snowflake account with the ACCOUNTADMIN role
  3. Clone the lab repo into a Snowflake Git Integration workspace, or download the scripts/ folder and open the files in Snowsight or Cortex Code

Parameterized Imports & Reusable Code

0:20 - 0:45 01_parameterized_imports.sql

Right now, importing each Clarity table means writing a bespoke CTAS statement. For 50+ tables, that is 50+ scripts to maintain. We are going to replace that with one procedure and one config table.

2.1 The problem

Run Part A in the script to see the hand-coded approach:

SQL - The old way
CREATE OR REPLACE TABLE CURATED.DIM_PATIENT AS
SELECT
    PAT_ID, PAT_MRN, PAT_FIRST_NAME, PAT_LAST_NAME,
    BIRTH_DATE, SSN, ADDRESS_LINE_1, CITY, STATE,
    ZIP_CODE, PHONE, EMAIL, GENDER,
    CURRENT_TIMESTAMP() AS LOADED_AT
FROM RAW.PATIENT_DIM;

Now imagine writing that for every table. Every one is slightly different. Every one can have a typo.

2.2 The config-driven approach

Check the config table that defines each import:

SQL
SELECT * FROM BUH_AUTOMATION_LAB.CURATED.IMPORT_CONFIG;

2.3 Build the procedure

Run Part C in the script to create the RUN_IMPORT procedure. This single procedure reads config, builds dynamic SQL, executes the import, and logs what it did.

2.4 Run the imports

SQL
CALL CURATED.RUN_IMPORT('PATIENT_DIM', 'BATCH-2024-10-25-001');
CALL CURATED.RUN_IMPORT('ENCOUNTER_FACT', 'BATCH-2024-10-25-001');
CALL CURATED.RUN_IMPORT('ORDERS', 'BATCH-2024-10-25-001');

2.5 Verify

SQL
-- Config should show SUCCESS for all three
SELECT SOURCE_TABLE, TARGET_TABLE, LAST_RUN_TS, LAST_RUN_STATUS
FROM CURATED.IMPORT_CONFIG;

-- Log entries for the batch
SELECT * FROM LOGS.RUN_LOG ORDER BY LOGGED_AT DESC LIMIT 10;
Key insight Adding a new Clarity table is now a single INSERT into IMPORT_CONFIG - no new code, no new script, no new deployment.

2.6 Bonus: run all imports in one call

SQL
CALL CURATED.RUN_ALL_IMPORTS('BATCH-2024-10-25-002');

Checkpoint

All three config rows show LAST_RUN_STATUS = SUCCESS. DIM_PATIENT, FACT_ENCOUNTER, and FACT_ORDERS exist in CURATED with BATCH_ID and LOADED_AT columns.

Resilient Vendor File Ingestion

0:45 - 1:05 02_vendor_ingestion.sql

External vendor lab files are messy. Columns appear and disappear. Required fields go missing. Your pipeline needs to handle this without crashing and without silently loading bad data.

3.1 Explore the three payloads

SQL
-- Good batch: matches expected schema
SELECT * FROM VENDOR_LANDING.VENDOR_LAB_BATCH_GOOD;

-- Drifted batch: has extra columns the vendor added
SELECT * FROM VENDOR_LANDING.VENDOR_LAB_BATCH_DRIFTED;

-- Invalid batch: missing required fields, bad formats
SELECT * FROM VENDOR_LANDING.VENDOR_LAB_BATCH_INVALID;

3.2 Build the validator

Run Part B in the script to create the validation function. It checks each row against business rules and returns a pass/fail verdict with specific reasons.

3.3 Process each batch

SQL
-- Good batch: all rows accepted
CALL VENDOR_LANDING.PROCESS_VENDOR_BATCH('VENDOR_LAB_BATCH_GOOD', 'GOOD-001');

-- Drifted batch: rows accepted, but drift logged as WARN
CALL VENDOR_LANDING.PROCESS_VENDOR_BATCH('VENDOR_LAB_BATCH_DRIFTED', 'DRIFT-001');

-- Invalid batch: bad rows quarantined with reasons
CALL VENDOR_LANDING.PROCESS_VENDOR_BATCH('VENDOR_LAB_BATCH_INVALID', 'INVALID-001');

3.4 Inspect results

SQL
-- 7 accepted, 4 quarantined
SELECT 'ACCEPTED' AS STATUS, COUNT(*) AS CNT FROM VENDOR_LANDING.VENDOR_LAB_ACCEPTED
UNION ALL
SELECT 'QUARANTINED', COUNT(*) FROM VENDOR_LANDING.VENDOR_LAB_QUARANTINE;

-- See WHY rows were rejected
SELECT VENDOR_ID, PAT_MRN, BATCH_ID, REJECTION_REASONS::VARCHAR AS REASONS
FROM VENDOR_LANDING.VENDOR_LAB_QUARANTINE;
Expected output ACCEPTED: 7 rows (5 good + 2 drifted) | QUARANTINED: 4 rows (all from invalid batch) | WARN log entries for schema drift and quarantine count
Discussion: Idempotency Re-running a batch currently duplicates rows. In production, you would use MERGE or DELETE+INSERT keyed on BATCH_ID. The reset pattern is shown in Part F of the script.

Checkpoint

Accepted table has 7 rows. Quarantine has 4 rows with specific rejection reasons as arrays. The log shows WARN entries for drift and quarantine counts.

Centralized Logging & Error Reporting

1:05 - 1:25 03_logging_and_monitoring.sql

Every procedure you built in the previous steps has been writing to the same RUN_LOG table. Now you will query it as a single pane of glass for pipeline observability.

4.1 View all log entries

SQL
SELECT * FROM LOGS.RUN_LOG ORDER BY LOGGED_AT DESC;

4.2 Build the batch health view

Run Parts B and C in the script. The BATCH_HEALTH view shows a RED/YELLOW/GREEN status per batch:

SQL
SELECT * FROM LOGS.BATCH_HEALTH;
Expected output BATCH and GOOD batches show GREEN. DRIFT batch shows YELLOW (warnings). INVALID batch shows YELLOW (quarantine warnings). Any batch with ERRORs would show RED.

4.3 Extract structured detail from VARIANT

SQL
SELECT
    RUN_ID,
    MESSAGE,
    DETAIL:rows_loaded::NUMBER AS ROWS_LOADED,
    DETAIL:target::VARCHAR AS TARGET_TABLE
FROM LOGS.RUN_LOG
WHERE DETAIL:rows_loaded IS NOT NULL;

4.4 Reusable logger

Run Part D to create a generic LOG_EVENT procedure. Any future procedure can call it for consistent logging.

Production extensions Event tables (SYSTEM$LOG) capture system-level telemetry automatically. Snowflake Alerts can watch RUN_LOG and email on errors. Both are discussed in Parts E and F of the script.

Checkpoint

BATCH_HEALTH view returns colored status per batch. Structured detail fields are queryable from the VARIANT column. The centralized logger works.

Governance, RBAC & Masking

1:25 - 1:45 04_governance_rbac_masking.sql

Right now, every role can see every SSN, every phone number, and every encounter. That is not acceptable for production. You will apply reusable masking policies and row-access controls and test them across three roles.

5.1 See the problem

SQL
-- All PII visible right now
SELECT PAT_FIRST_NAME, PAT_LAST_NAME, SSN, PHONE, EMAIL
FROM RAW.PATIENT_DIM LIMIT 5;

5.2 Create and apply masking policies

Run Parts B and C in the script. The SSN_MASK and PII_STRING_MASK policies are created once in the GOVERNANCE schema and applied to multiple columns.

5.3 Test across roles

On a trial account your user inherits ACCOUNTADMIN, so a plain USE ROLE switch still resolves the admin check as TRUE. We use EXECUTE USING POLICY_CONTEXT to simulate each role cleanly:

SQL
-- ADMIN sees everything
EXECUTE USING POLICY_CONTEXT(
    CURRENT_ROLE => 'BUH_LAB_ADMIN'
)
SELECT PAT_FIRST_NAME, PAT_LAST_NAME, SSN, PHONE, EMAIL
FROM BUH_AUTOMATION_LAB.RAW.PATIENT_DIM LIMIT 3;

-- CLINICIAN sees names and phone, SSN last-4 only
EXECUTE USING POLICY_CONTEXT(
    CURRENT_ROLE => 'BUH_LAB_CLINICIAN'
)
SELECT PAT_FIRST_NAME, PAT_LAST_NAME, SSN, PHONE, EMAIL
FROM BUH_AUTOMATION_LAB.RAW.PATIENT_DIM LIMIT 3;

-- ANALYST sees masked everything
EXECUTE USING POLICY_CONTEXT(
    CURRENT_ROLE => 'BUH_LAB_ANALYST'
)
SELECT PAT_FIRST_NAME, PAT_LAST_NAME, SSN, PHONE, EMAIL
FROM BUH_AUTOMATION_LAB.RAW.PATIENT_DIM LIMIT 3;

5.4 Row-access policy

Run Part E. Clinicians can only see encounters from departments they are mapped to (Cardiology and Primary Care). Analysts and admins see everything.

5.5 Audit existing policies

SQL
SHOW MASKING POLICIES IN DATABASE BUH_AUTOMATION_LAB;
SHOW ROW ACCESS POLICIES IN DATABASE BUH_AUTOMATION_LAB;
Important Masking policies on a base table do NOT automatically propagate to CTAS copies. CURATED tables created by RUN_IMPORT are unprotected unless you also apply policies there, use secure views, or use tag-based masking (which does propagate through lineage).

Checkpoint

SSN shows differently for each role. Clinician sees 4 encounters (Cardiology + Primary Care), not all 10. Policy audit queries return the applied policies.

AI & Multimodal Capstone

1:45 - 1:55 05_ai_multimodal_capstone.sql

This optional module shows how AI fits into the pipeline you already built - not as a separate initiative, but as an accelerator for annotation, extraction, and cataloging.

Cortex requirement Parts A-C use SNOWFLAKE.CORTEX.AI_COMPLETE and AI_EXTRACT. If these are not enabled in your account, use the commented-out fallback queries in the script. The learning point is the pattern, not the model output.

6.1 Summarize clinical notes

SQL
SELECT
    NOTE_ID,
    NOTE_TYPE,
    SNOWFLAKE.CORTEX.AI_COMPLETE(
        'llama3.1-8b',
        'Summarize this clinical note in 2-3 sentences. '
        || 'Extract: primary diagnosis, key findings, and plan. Note: '
        || NOTE_TEXT
    ) AS AI_SUMMARY
FROM RAW.CLINICAL_NOTES;

6.2 Extract structured fields

SQL
SELECT
    NOTE_ID,
    SNOWFLAKE.CORTEX.AI_EXTRACT(
        NOTE_TEXT,
        ARRAY_CONSTRUCT('primary_diagnosis', 'medications', 'follow_up_plan')
    ) AS EXTRACTED
FROM RAW.CLINICAL_NOTES;

6.3 Where AI fits in the pipeline

Pipeline StageAI Application
Parameterized importsAI_COMPLETE for auto-generating column descriptions
Vendor ingestionAI_EXTRACT to normalize inconsistent vendor formats
LoggingAI_SUMMARIZE on error logs to surface patterns
GovernanceSYSTEM$CLASSIFY to detect PII automatically
Key takeaway The work in Scripts 01-04 is the foundation. AI accelerates it - it does not replace it.
