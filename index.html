Shared Workspaces & Git Integration

0:10 - 0:25 01_workspaces_and_git.sql

Workspaces are Snowflake's built-in way to connect a Git repo (GitHub, GitLab, Azure DevOps) to your Snowflake account. This lab itself was delivered via a Git workspace.

What you can do

  • Browse - Navigate repo files directly in Snowsight
  • Run - Execute .sql files from the repo without downloading
  • Version - Every change goes through Git (history, review, rollback)
  • Collaborate - Team members clone and run the same versioned code

How it works

SQL - Creating a Git integration
-- Step 1: API integration (connects Snowflake to your Git provider)
CREATE OR REPLACE API INTEGRATION github_integration
  API_PROVIDER = GIT_HTTPS_API
  API_ALLOWED_PREFIXES = ('https://github.com/your-org/')
  ENABLED = TRUE;

-- Step 2: Git repository object
CREATE OR REPLACE GIT REPOSITORY BUH_HOL.RAW.LAB_REPO
  API_INTEGRATION = github_integration
  ORIGIN = 'https://github.com/daltonryan6/buh-automation-hol.git';

-- Step 3: Fetch and browse
ALTER GIT REPOSITORY BUH_HOL.RAW.LAB_REPO FETCH;
LS @BUH_HOL.RAW.LAB_REPO/branches/main/scripts/;

Why this matters

Without Git workspacesWith Git workspaces
SQL in local files, Slack, shared drivesSQL versioned in Git with history
No code review, no rollbackPull requests and peer review
"Which version is in prod?" - unknownTraceable: commit abc123 is in prod
Onboarding = copying filesClone and run

Checkpoint

You understand how Git integrations, repository objects, and workspaces connect your team's code to Snowflake.

Dynamic Tables

0:25 - 0:55 02_dynamic_tables.sql

Dynamic tables flip ETL on its head: you declare what the result should look like, and Snowflake figures out when to refresh it. No scheduling, no orchestration, no manual MERGE scripts.

2.1 Build the CURATED layer

Run Part B in the script. Each dynamic table declares a transformation and a TARGET_LAG (how fresh data needs to be):

SQL - Example: DIM_PATIENT
CREATE OR REPLACE DYNAMIC TABLE BUH_HOL.CURATED.DIM_PATIENT
  TARGET_LAG = '1 minute'
  WAREHOUSE = COMPUTE_WH
AS
SELECT
    PAT_ID, PAT_MRN,
    INITCAP(PAT_FIRST_NAME) AS FIRST_NAME,
    INITCAP(PAT_LAST_NAME) AS LAST_NAME,
    BIRTH_DATE,
    DATEDIFF('year', BIRTH_DATE, CURRENT_DATE()) AS AGE,
    SSN, PHONE, EMAIL, GENDER,
    LOAD_TS AS SOURCE_LOADED_AT
FROM BUH_HOL.RAW.PATIENT_DIM;

2.2 Build the GOLD layer

GOLD dynamic tables read from CURATED, which reads from RAW. The whole graph refreshes automatically when RAW changes.

SQL
SELECT * FROM BUH_HOL.GOLD.PATIENT_ENCOUNTER_SUMMARY ORDER BY TOTAL_CHARGES DESC;
SELECT * FROM BUH_HOL.GOLD.DEPARTMENT_DASHBOARD ORDER BY TOTAL_CHARGES DESC;
SELECT * FROM BUH_HOL.GOLD.ABNORMAL_RESULTS_SUMMARY;

2.3 Watch it refresh

Insert a new patient into RAW and watch it propagate through the pipeline automatically:

SQL
-- Insert new patient
INSERT INTO BUH_HOL.RAW.PATIENT_DIM
  (PAT_ID,PAT_MRN,PAT_FIRST_NAME,PAT_LAST_NAME,BIRTH_DATE,SSN,
   ADDRESS_LINE_1,CITY,STATE,ZIP_CODE,PHONE,EMAIL,PRIM_LANGUAGE,GENDER)
VALUES ('P100009','MRN-900009','Elena','Vasquez','2001-02-14',
        '999-00-1111','500 Atwells Ave','Providence','RI','02909',
        '401-555-0109','evasquez@example.com','Spanish','Female');

-- Wait ~1 minute, then check CURATED and GOLD
SELECT * FROM BUH_HOL.CURATED.DIM_PATIENT WHERE PAT_ID = 'P100009';
SELECT * FROM BUH_HOL.GOLD.PATIENT_ENCOUNTER_SUMMARY WHERE PAT_ID = 'P100009';

2.4 Monitor pipeline health

SQL
SELECT NAME, STATE, REFRESH_START_TIME,
       DATEDIFF('second', REFRESH_START_TIME, REFRESH_END_TIME) AS SECONDS
FROM TABLE(INFORMATION_SCHEMA.DYNAMIC_TABLE_REFRESH_HISTORY())
ORDER BY REFRESH_START_TIME DESC LIMIT 15;
TARGET_LAG guidance 1 minute = near real-time dashboards. 15 minutes = operational reporting. 1 hour = standard analytics. DOWNSTREAM = refresh only when a consumer needs it.

Power BI, Iceberg Tables & Microsoft Fabric

0:55 - 1:20 03_powerbi_iceberg_fabric.sql

3.1 Power BI connection options

OptionHow it worksSnowflake costBest for
DirectQueryPower BI sends SQL to Snowflake at query timeWarehouse runs during dashboard useOperational dashboards, moderate concurrency
ImportPower BI extracts data on a scheduleWarehouse runs only during refreshExecutive dashboards refreshed daily
Direct Lake (Fabric)Snowflake writes Iceberg to OneLake; Power BI reads ParquetWarehouse runs only to write IcebergMinimizing Snowflake compute for BI

3.2 Fabric consumption - what to watch

Fabric CU overconsumption All Fabric workloads (Power BI, Spark, SQL endpoint) share one pool of Capacity Units. Direct Lake reads consume CUs from that pool. If you undersize the capacity, workloads queue and throttle. The cheapest path: keep your pipeline in Snowflake, write only GOLD as Iceberg to OneLake, and size Fabric capacity for BI read load only.

3.3 Iceberg tables (hands-on)

Iceberg tables use the same SQL as regular Snowflake tables, but the data is stored in open Parquet format. Any engine that reads Iceberg can access it.

SQL
-- See the Iceberg table created in the script
SELECT * FROM BUH_HOL.GOLD.DEPT_DASHBOARD_ICEBERG
ORDER BY TOTAL_CHARGES DESC;

3.4 Iceberg for OneLake (the Microsoft-recommended pattern)

The setup requires an external volume pointing to OneLake and a Fabric workspace. The script walks through the SQL; in production you would:

  1. Create an external volume pointing to azure://onelake.dfs.fabric.microsoft.com/...
  2. Create Iceberg tables using that volume
  3. Power BI connects via Direct Lake - no Snowflake warehouse needed for reads

3.5 Purview integration

Purview can scan Snowflake accounts (tables, views, stored procedures, lineage). For Iceberg tables in OneLake, Purview sees both the Snowflake definition and the Parquet files. However, Snowflake tags and Purview sensitivity labels are separate systems - they do not auto-sync.

3.6 When to use which table type

LayerRecommendedWhy
RAWSnowflake defaultFast ingest, time travel, streams
CURATEDSnowflake default (dynamic tables)Joins, transforms, incremental refresh
GOLD / DatamartIceberg (to OneLake)Open format, Power BI Direct Lake, no SF compute for BI

Checkpoint

You understand the three Power BI options, why Fabric CUs are the cost lever to watch, how Iceberg tables work, and that Purview/Snowflake tags are separate systems.

Tags, Sensitivity Labels & Governance

1:20 - 1:45 04_tags_and_governance.sql

4.1 Where do tags apply?

ObjectExample tag
Warehousecost_center = 'Research'
Databasedata_domain = 'Clinical'
Schemadata_layer = 'RAW'
Table / Viewcontains_phi = 'Yes'
Columnpii_type = 'SSN'

Tags cannot be applied to individual rows, stages, file formats, users, or roles.

4.2 Create and apply tags

Run Parts B and C in the script to create PII_TYPE, SENSITIVITY, DATA_DOMAIN, and COST_CENTER tags, then apply them to columns and objects.

4.3 Query tags - find all PII

SQL
SELECT OBJECT_NAME AS TABLE_NAME, COLUMN_NAME, TAG_VALUE AS PII_TYPE
FROM SNOWFLAKE.ACCOUNT_USAGE.TAG_REFERENCES
WHERE TAG_NAME = 'PII_TYPE' AND DOMAIN = 'COLUMN'
  AND OBJECT_DATABASE = 'BUH_HOL'
ORDER BY TABLE_NAME, COLUMN_NAME;

4.4 Tag-based masking

Instead of attaching masking policies column by column, attach them to a tag. Every column with that tag is automatically protected.

SQL
-- Attach masking policy to tag (not to columns!)
ALTER TAG BUH_HOL.GOVERNANCE.PII_TYPE SET
  MASKING POLICY BUH_HOL.GOVERNANCE.MASK_PII_STRING;

4.5 Test masking across roles

4.6 Automatic classification

Snowflake can auto-detect PII using SYSTEM$CLASSIFY. It scans column names and data patterns to recommend tags. In production, a classification profile runs this on a schedule across your database.

Putting It Together

1:45 - 1:55 05_putting_it_together.sql

The architecture you built

  [Git Repo] --> [Snowflake Workspace]
       |
       v
  RAW (default tables - Clarity extracts)
       |  dynamic tables auto-refresh
       v
  CURATED (DIM_PATIENT, FACT_ENCOUNTER, FACT_LAB_RESULTS)
       |  dynamic tables auto-refresh
       v
  GOLD (PATIENT_ENCOUNTER_SUMMARY, DEPT_DASHBOARD, ABNORMAL_RESULTS)
       |
       +--> Snowflake default tables (analytics, AI, sharing)
       |
       +--> Iceberg tables in OneLake (Power BI Direct Lake)

  GOVERNANCE layer (tags + masking policies) applies across ALL layers

Verify end-to-end

SQL
SELECT 'RAW.PATIENT_DIM' AS LAYER, COUNT(*) AS ROWS FROM BUH_HOL.RAW.PATIENT_DIM
UNION ALL SELECT 'CURATED.DIM_PATIENT', COUNT(*) FROM BUH_HOL.CURATED.DIM_PATIENT
UNION ALL SELECT 'CURATED.FACT_ENCOUNTER', COUNT(*) FROM BUH_HOL.CURATED.FACT_ENCOUNTER
UNION ALL SELECT 'GOLD.PATIENT_ENCOUNTER_SUMMARY', COUNT(*) FROM BUH_HOL.GOLD.PATIENT_ENCOUNTER_SUMMARY
UNION ALL SELECT 'GOLD.DEPARTMENT_DASHBOARD', COUNT(*) FROM BUH_HOL.GOLD.DEPARTMENT_DASHBOARD
ORDER BY LAYER;
